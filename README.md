# Mini NPU Simulator

AI 가속기(NPU)의 핵심 연산인 **MAC(Multiply-Accumulate, 곱셈-누적)** 연산의 동작 원리를 파이썬 순수 문법(표준 라이브러리)으로 직접 구현하고, 크기별 연산량 및 순차 실행 특성을 분석하며 부동소수점 오차 처리 정책을 검증하는 콘솔 애플리케이션입니다.

---

## 1. 프로젝트 소개

### 개발 목적
- **AI 핵심 연산의 원리 이해**: 합성곱 신경망(CNN)과 선형 변환(Fully-Connected) 등 주요 딥러닝 모델의 기본 연산 단위인 위치별 곱셈-누적(MAC) 연산을 외부 라이브러리(NumPy 등) 없이 순수 2차원 리스트와 중첩 반복문으로 구현합니다.
- **패턴 인식 및 유사도 판별**: 입력된 숫자 패턴과 필터(십자가 `Cross`, `X`) 간의 MAC 연산 점수를 비교하여 더 유사한 형태를 자동으로 판별합니다.
- **수치 안정성 및 예외 처리**: 컴퓨터의 2진수 부동소수점 누적 오차를 고려한 허용오차(epsilon) 비교 정책과 다양한 입력 라벨 표기를 표준화하는 데이터 정규화 파이프라인을 구축합니다.
- **연산량 및 복잡도 분석**: 데이터 크기($N \times N$) 증가에 따른 연산 횟수($N^2$)와 순차 연산 시간의 관계를 실측하여, 대규모 연산에서 병렬 하드웨어(NPU)가 도입되는 기술적 배경을 이해합니다.

### 주요 기능
1. **모드 1 (사용자 직접 입력 모드)**: 3×3 필터 A, B와 패턴을 콘솔에서 직접 입력받아 점수 계산, 판정(A / B / 판정 불가), 3×3 MAC 연산 시간 측정을 수행합니다.
2. **모드 2 (JSON 데이터 자동 분석 모드)**: `data.json`의 다중 크기(5×5, 13×13, 25×25) 필터 및 패턴을 일괄 로드하여 검증, 판정(PASS/FAIL), 크기별 벤치마크 및 결과 요약 리포트를 출력합니다.
3. **입력 검증 및 오류 회복**: 사용자 입력 시 열 개수 불일치나 문자 입력 시 프로그램을 종료하지 않고 안내 후 재입력을 유도하며, JSON 모드에서는 불량 데이터가 있어도 해당 케이스만 FAIL 처리하고 전체 분석을 완주합니다.

## 2. 과제 핵심 개념 해설 (Learning Objectives)

미션 가이드에 명시된 핵심 과제 목표에 대한 분석 및 해설입니다:

| 핵심 질문 | 분석 및 해설 |
|:---|:---|
| **1. MAC 연산이란 무엇이며, AI에서 왜 중요한가?** | **곱셈 후 누적(Multiply-Accumulate)**하는 연산으로, 입력 데이터 $X$와 가중치 $W$의 원소별 곱을 모두 합산하는 신경망 순전파(Forward Pass)의 기본 단위입니다. 딥러닝 추론 과정에서 대량으로 반복 발생하므로, 전체 연산 시스템의 처리 속도와 에너지 효율을 좌우하는 핵심 연산입니다. |
| **2. 유사도(점수) 계산의 원리와 음수 해석은?** | 입력 패턴과 필터의 동일한 위치 좌표 $(i, j)$에 대해 $Pattern[i][j] \times Filter[i][j]$를 계산합니다. 양수 가중치가 겹칠수록 점수가 증가(활성화)하며, 0은 무영향입니다. **가중치가 음수인 경우** 해당 위치에 패턴이 존재할 때 점수를 차감(억제, Suppression)하여 특정 노이즈를 걸러내거나 윤곽선(Edge)의 명암 대비를 감지하는 역할을 합니다. |
| **3. 라벨을 표준화(정규화)하는 이유는?** | 데이터 소스(JSON, 사용자 입력)마다 `'+'`, `'x'`, `'X'`, `'cross'`, `'Cross'` 등 표기 방식이 제각각입니다. 이를 전처리 단계에서 단일 표준 라벨(`Cross`, `X`)로 통일하지 않으면, 계산이 수학적으로 정확해도 단순 문자열 불일치로 인한 오판정(False FAIL)이 발생하므로 데이터 정규화가 필수적입니다. |
| **4. 부동소수점 오차와 epsilon 정책이 필요한 이유는?** | 컴퓨터는 실수를 2진수(IEEE 754 배정밀도)로 표현하므로 $0.1$과 같은 십진 소수를 유한 비트로 저장할 때 오차가 누적됩니다. 예컨대 9번의 $0.1$ 덧셈은 $0.9$가 아닌 $0.8999999999999999$가 됩니다. 따라서 단순 등호(`==`) 비교 대신 허용오차 $\|a - b\| < \text{EPSILON}(10^{-9})$ 범위를 동점으로 판정해야 잘못된 대소 판별을 방지할 수 있습니다. |
| **5. 크기 증가에 따른 시간 복잡도 $O(N^2)$의 근거는?** | $N \times N$ 행렬의 모든 칸을 외부 행 루프 $N$회, 내부 열 루프 $N$회 중첩 방문하므로 곱셈-누적 횟수는 정확히 $N^2$번 발생합니다. 따라서 순차 알고리즘의 시간 복잡도는 $O(N^2)$에 비례하며, 크기가 커질수록 연산량이 제곱으로 증가함을 설명할 수 있습니다. |
| **6. 실패 케이스 진단 및 3대 분류 기준은?** | 실패(FAIL) 발생 시 맹목적으로 로직을 수정하지 않고, **① 데이터/스키마 문제** (크기 불일치, 누락, 파싱 불가), **② 로직 문제** (점수 차이가 유의미함에도 판정 오판), **③ 수치 비교 문제** (부동소수점 오차 또는 설계된 동점으로 인한 미결정)로 분리 진단하여 올바른 개선책을 도출합니다. |

## 4. `data.json` 구조 및 스키마 유효성 규칙

### 1) 데이터 구조 및 공식 가이드 완벽 재현
`data.json` 파일은 코디세이 공식 미션 가이드에 제시된 스펙과 100% 동일하게 구성되어 있습니다:
- **필터 3종**: `size_5`, `size_13`, `size_25` (Cross, X 필터)
- **패턴 6종**: `size_5_1`, `size_5_2`, `size_13_1`, `size_13_2`, `size_25_1`, `size_25_2`

### 2) 원본 데이터 파일과의 호환성
- `tools/make_data.py`는 과제 공식 슬라이드에 정의된 값(가운데 칸 0.9, 7.5, 4.9 등)과 라벨(`+`, `x`, `X`, `Cross`)을 그대로 프로그래밍하여 생성한 표준 검증 데이터입니다.
- **교육 기관에서 별도로 배포한 원본 `data.json`이 있는 경우**, 본 프로젝트 루트 디렉토리의 `data.json` 위치에 그대로 덮어쓰기만 하면 어떠한 코드 수정 없이도 완벽하게 동일하게 로드되어 분석됩니다.

### 3) 스키마 파싱 및 유효성 검증 규칙
- **키 파싱 규칙**: `size_{N}_{idx}` 패턴 키에서 `split('_')`을 통해 크기 $N$을 정수로 추출합니다.
  - 올바른 예시 키: `size_5_1`, `size_13_2`, `size_25_1`
  - 잘못된 형식(예: `s5_1`, `pattern_13`) 유입 시: `패턴 키 형식 오류` 메시지와 함께 해당 케이스만 `FAIL (스키마)` 처리됩니다.
- **필터 매핑 검증**: 추출된 크기 $N$에 대해 `filters["size_{N}"]` 및 그 내부의 `cross`, `x` 필터 행렬이 정확히 $N \times N$ 정사각 형태인지 검증합니다. 누락 시 `FAIL (스키마)`로 안전하게 기록됩니다.
- **라벨 매핑 규칙**:
  - `'+'`, `'cross'`, `'plus'` $\rightarrow$ `'Cross'`
  - `'x'`, `'ex'` $\rightarrow$ `'X'`
  - 지원하지 않는 미등록 라벨 유입 시: `None`을 반환하여 비정상 종료 없이 `FAIL (스키마: 정규화 불가능한 라벨)`로 격리됩니다.

### 4) 신규 라벨 확장 개발자 체크리스트
향후 새로운 패턴(예: 원형 `'Circle'`, 다이아몬드 `'Diamond'`)을 추가할 경우 수정해야 할 파일 목록입니다:

2. `src/judge.py`: `judge()` 함수의 다자간 비교 로직 확장 (2개 비교 $\rightarrow$ 다중 필터 최댓값 탐색)
3. `tests/test_all.py`: 신규 라벨 정규화 및 점수 비교 단위 테스트 추가
4. `tools/make_data.py` (또는 `data.json`): 신규 필터 매트릭스 및 expected 라벨 추가

## 5. 핵심 구현 방식 및 정책

### 1) 2차원 배열과 메모리 격리 (`src/matrix.py`)
- Python에서 `[[0]*n]*n` 형태로 2차원 배열을 생성하면 동일한 행 객체가 얕은 복사(shallow copy)되어 한 칸의 값을 수정했을 때 전체 행의 값이 바뀌는 버그가 발생합니다.
- 독립된 메모리 행을 보장하기 위해 리스트 컴프리헨션을 적용하였습니다:
  ```python
  def make_matrix(n, fill=0):
      return [[fill for _ in range(n)] for _ in range(n)]
  ```

### 2) 순수 반복문 기반 MAC 연산 (`src/mac.py`)
- 외부 라이브러리(NumPy) 없이 2차원 리스트의 각 좌표를 순회하며 곱셈과 덧셈을 직접 누적합니다:
  ```python
  def mac(pattern, filt):
      total = 0.0
      n = len(pattern)
      for i in range(n):
          for j in range(n):
              total += pattern[i][j] * filt[i][j]
      return total
  ```

### 3) 입력 검증 및 오류 회복 (`src/mode_input.py`)
- 모드 1 콘솔 입력 시 행당 원소 개수(`len(parts) != n`) 불일치와 숫자 변환 실패(`ValueError`)를 감지하여 구체적인 오류 원인을 안내하고 처음부터 재입력받도록 방어 처리하였습니다.

### 4) 부동소수점 허용오차(Epsilon) 상수 선택 근거 및 정책 (`src/judge.py`)
- **`EPSILON = 1e-9` 선택 근거**:
  - IEEE 754 배정밀도(Float64)의 기계 입실론(Machine Epsilon)은 약 $2.22 \times 10^{-16}$입니다.
  - 십진 소수($0.1, 0.3$ 등)의 누적 덧셈 과정에서 발생하는 오차 범위는 통상 $10^{-16} \sim 10^{-14}$ 수준입니다.
  - 반면 실제 데이터셋에서 의미 있는 최소 점수 차이는 $0.1$ 이상입니다.
  - 따라서 $10^{-9}$는 **기계적 누적 오차($10^{-15}$)보다 충분히 크고, 유의미한 점수 차이($10^{-1}$)보다 충분히 작은 안전한 경계값**으로 채택되었습니다.
- **데이터 스케일에 따른 확장 가이드**:
  - 만약 입력 행렬의 원소 값이 수백만 단위로 커진다면 절대오차 대신 상대오차($\frac{|a - b|}{\max(|a|, |b|)} < \epsilon$) 기준을 병행 적용하는 것이 권장됩니다.
- **모드별 동점 출력 정책의 의도적 차이**:
  - **모드 1**: 대화형 콘솔 사용자 친화성을 위해 직관적인 한국어 표기인 **`판정 불가`**로 출력합니다.
  - **모드 2**: 자동 채점 및 배치 리포트 작성을 위해 기계가 파싱하기 용이한 영문 식별자인 **`UNDECIDED`**로 출력하며, 기대 라벨(Cross 또는 X)과 불일치하므로 테스트 결과는 `FAIL`로 안전하게 분류 집계됩니다.

## 6. 콘솔 실행 화면 예시 및 출력 포맷 정책

### [출력 포맷 및 소수점 자리 정책]
- **점수 출력**: 가독성을 위해 소수점 첫째 자리(`.1f`)로 표기합니다. (예: `5.0`, `1.0`, `0.9`)

### 2) 실패 원인 정밀 분석 (10줄 이상 상세 서술)

1. **실패 케이스의 본질적 성격**: 이번 벤치마크에서 발생한 3건의 FAIL(`size_5_1`, `size_13_2`, `size_25_1`)은 프로그램의 코드 결함이나 구현 실수가 아니며, 데이터셋 설계자가 '수치적 동점 상황'을 의도적으로 부여한 검증용 케이스입니다.
2. **`size_5_1` 수치 분석**: X 패턴(1이 9칸)과 X 필터(모든 칸 0.1)의 MAC 연산은 $9 \times 0.1 = 0.9$가 기대되지만 부동소수점 누적으로 실제로는 `0.8999999999999999`가 계산됩니다. 반면 Cross 필터는 가운데 칸만 `0.9`이므로 겹치는 1칸과의 연산 결과 정확히 `0.9`가 됩니다.
3. **`size_13_2` 수치 분석**: 십자가 패턴(25칸)과 Cross 필터(모든 칸 0.3)의 연산은 $25 \times 0.3$으로 이론상 `7.5`이나 부동소수점 누적 합산값은 `7.499999999999997`이 됩니다. 반면 X 필터의 가운데 칸이 `7.5`로 지정되어 있어 X 점수 역시 `7.5`가 산출됩니다.
4. **`size_25_1` 수치 분석**: X 패턴(49칸)과 X 필터(모든 칸 0.1)의 연산 누적값은 `4.899999999999999`가 되며, Cross 필터 가운데 칸 `4.9`와 사실상 완벽한 동점을 이룹니다.
5. **단순 등호(`==`) 비교 시 발생하는 왜곡**: 만약 부동소수점 오차 정책 없이 `score_cross == score_x`로 동점을 판단하고 단순히 `>` 조건으로 판정했다면, `0.9 > 0.8999999999999999`로 인해 Cross 점수가 더 높은 것으로 판정되어 엉뚱하게 `Cross`라는 잘못된 판정 결과가 나오고 원인 파악이 어려운 '로직 오류'로 분류되었을 것입니다.
6. **Epsilon 정책의 효과**: 본 프로젝트에 도입된 `EPSILON = 1e-9` 정책을 통해 두 점수의 절대 차이($\|a - b\| < 10^{-9}$)가 기계적 오차 범위 내임을 감지하고 정상적으로 `UNDECIDED`(판정 불가)를 반환함으로써, 미세한 비트 오차에 의해 잘못된 판정이 내려지는 현상을 방지하고 '수치 비교 문제'로 정확히 분류할 수 있었습니다.
7. **라벨 정규화의 기여**: 데이터셋의 expected 라벨이 `'+'`나 소문자 `'x'` 등으로 일관되지 않은 상태로 제공되었으나, 전처리 단계의 `normalize_label()`이 이를 모두 표준 라벨(`Cross`, `X`)로 변환하여 문자열 불일치로 인한 거짓 실패(False Failure)를 완벽히 예방했습니다.
8. **데이터 유효성 검증 체계**: 행렬의 크기가 $N \times N$인지 검사하는 `is_square()` 및 키 파싱 방어 코드를 통해, 비정상적인 데이터가 유입되더라도 전체 프로세스가 크래시되지 않고 해당 케이스만 안전하게 격리되어 처리됨을 확인했습니다.
9. **향후 모델 및 데이터셋 개선 방향**: 실제 AI 모델 환경에서 이와 같은 동점 또는 판정 모호성을 해결하기 위해서는 필터의 가중치 초기화 시 대칭성을 깨뜨리는 난수(Random Weight)를 적용하거나, 필터 간 직교성(Orthogonality)을 강화하는 학습 손실 함수(Loss Function)를 추가해야 합니다.

### 3) 시간 복잡도 분석 ($O(N^2)$) 및 실측 벤치마크

#### 측정 환경 명시 (벤치마크 하드웨어)
- **CPU**: 11th Gen Intel(R) Core(TM) i7-1165G7 @ 2.80GHz (4 Cores, 8 Threads)
- **OS**: Windows 11 Home (64-bit) / Python 3.14.0
- **측정 방식**: I/O(콘솔 출력, 파일 읽기)를 배제하고 순수 `mac()` 연산 루프만 `time.perf_counter()`로 10회 반복 측정 후 평균값 산출 (정밀도 보장을 위해 백그라운드 고부하 프로세스 배제)

| 패턴 크기 ($N \times N$) | 곱셈·누적 연산 횟수 ($N^2$) | 실측 평균 시간 (ms) | 이론적 연산량 비율 ($N^2 / 9$) | 실측 시간 증가 비율 (3×3 대비) |
|:---:|:---:|:---:|:---:|:---:|
| **3×3** | 9회 | 약 0.0011 ms | 1.0배 | 1.0배 |
| **5×5** | 25회 | 약 0.0016 ms | 2.8배 | 약 1.5배 |
| **13×13** | 169회 | 약 0.0085 ms | 18.8배 | 약 7.7배 |
| **25×25** | 625회 | 약 0.0296 ms | 69.4배 | 약 26.9배 |

> **재현성 안내**: 절대적인 측정 시간(ms)은 각 컴퓨터의 CPU 클럭과 OS 스케줄링 상태에 따라 약간의 차이가 있을 수 있으나, $N^2$ 증가에 따른 연산 시간 증가 곡선은 모든 환경에서 동일하게 재현됩니다.

#### 복잡도 및 고정 오버헤드 분석
- **$O(N^2)$ 시간 복잡도의 근거**: 2차원 행렬 순회는 외부 for문 $N$번, 내부 for문 $N$번 총 $N \times N = N^2$번의 곱셈 및 누적 덧셈 연산을 순차적으로 수행하므로 알고리즘의 시간 복잡도는 이론상 정확히 $O(N^2)$입니다.
- **실측 증가 비율이 $N^2$ 비율(69배)보다 작은 이유 (고정 오버헤드)**:
  - 3×3과 같은 작은 크기에서는 실제 곱셈 연산 시간보다 파이썬 인터프리터의 함수 호출(Function call), 지역 변수 스택 프레임 생성, 루프 진입 등 고정 비용(Fixed Overhead)이 차지하는 비중이 큽니다.
  - 데이터 크기가 25×25로 커질수록 고정 비용의 비율이 상대적으로 줄어들고 순수 연산 루프가 지배하게 되면서 점진적으로 $N^2$ 증가 추세에 근접하게 됩니다.

## 8. 대규모 데이터($1000 \times 1000$) 확장 시 이슈 및 최적화 로드맵 (Deep Dive)

입력 패턴과 필터의 크기가 $1000 \times 1000$ ($N=1000$) 규모로 대형화될 때 발생하는 시스템 병목과 구체적인 최적화 우선순위 분석입니다:

### 1) 시간 및 메모리 영향 예측
- **연산량 폭증 ($10^6$회)**:
  - $N=1000$일 때 1개 필터당 MAC 연산 횟수는 $1000 \times 1000 = \mathbf{1,000,000\text{회}}$(1백만 번)입니다.
  - $25 \times 25$ ($625$회) 연산에 약 $0.03\text{ ms}$가 소요되었으므로, 단순 $O(N^2)$ 선형 확장 시 단일 MAC 호출에 약 **$48\text{ ms}$**(0.05초)가 소요됩니다.
  - 만약 실제 딥러닝 모델처럼 수백~수천 개의 필터를 적용한다면 1장의 이미지를 처리하는 데만 수십 초 이상 지연되어 실시간 처리가 불가능해집니다.
- **메모리 사용량 및 공간 복잡도 ($O(N^2)$)**:
  - 순수 64비트 실수 배열(Float64) 기준: $1000 \times 1000 \times 8\text{ Byte} \approx \mathbf{8\text{ MB}}$
  - 하지만 파이썬의 중첩 리스트(`list of lists`)는 각 float 객체에 대한 포인터 배열 오버헤드가 추가되어 행렬 1개당 약 **$24 \sim 32\text{ MB}$**의 힙 메모리를 소모합니다.
  - 이는 CPU의 고속 L1/L2 캐시 크기(통상 L1: 32~48KB, L2: 512KB~1.25MB)를 완전히 초과하여 극심한 **캐시 미스(Cache Miss)와 메모리 대역폭 병목**을 유발합니다.

### 2) 구체적 최적화 우선순위 (Roadmap)

| 우선순위 | 최적화 기법 | 구체적 구현 방식 및 기대 효과 |
|:---:|:---|:---|
| **1순위** | **메모리 평탄화 및 캐시 지역성 확보** | 2차원 리스트의 중첩 포인터 참조를 제거하고 1차원 연속 메모리 버퍼(`array` 또는 `1D list`)로 변환합니다. 공간 지역성(Spatial Locality)이 극대화되어 캐시 적중률이 비약적으로 상승합니다. (본 프로젝트 보너스 과제에서 1.3~1.8배 향상 검증 완료) |
| **2순위** | **캐시 블록 분할 (Tiling / Blocking)** | $1000 \times 1000$ 전체를 한 번에 순회하지 않고, CPU L1/L2 캐시에 쏙 들어가는 $32 \times 32$ 또는 $64 \times 64$ 크기의 타일(Tile) 단위로 쪼개어 연산합니다. 캐시 스래싱(Cache Thrashing)을 방지하여 메모리 왕복 대기 시간을 최소화합니다. |
| **3순위** | **SIMD 벡터화 명령어 활용** | CPU의 AVX2 (256-bit) 또는 AVX-512 명령어를 적용하여 1클럭에 8개~16개의 부동소수점 곱셈-누적을 동시에 실행합니다. (C-Extension 또는 NumPy 연동 시 10배~30배 속도 향상) |
| **4순위** | **멀티스레딩 병렬화 (Parallelism)** | 독립적인 행/블록 단위로 연산을 분할하여 CPU의 멀티코어(예: 4코어 8스레드)로 분산 처리합니다. (단, Python GIL 제한을 극복하기 위해 C 레벨 스레딩이나 멀티프로세싱 활용 필수) |
| **5순위** | **전용 하드웨어 NPU 오프로딩 (Systolic Array)** | CPU의 범용 ALU를 거치지 않고, 수천 개의 2차원 격자형 곱셈-누적기로 구성된 NPU 시스톨릭 어레이(Systolic Array)로 행렬을 스트리밍하여 한 클럭당 수백 번의 MAC을 병렬 처리합니다. |

## 9. 하드웨어 구조 비교: CPU vs GPU vs NPU

대규모 MAC 연산 처리 시 프로세서 구조별 구체적 하드웨어 수치 및 성능 특성 비교입니다:

| 비교 항목 | CPU (중앙처리장치) | GPU (그래픽처리장치) | NPU (신경망처리장치) |
|:---|:---|:---|:---|
| **대표 하드웨어 구성** | 4 ~ 16개 고성능 코어 (ALU) | 2,000 ~ 10,000+ 단순 스트림 코어 | 수천~수만 개의 격자형 MAC 전용 연산기 (Systolic Array) |
| **처리 방식** | **직렬 순차 처리** (Serial) | **대규모 범용 병렬 처리** (SIMT) | **데이터 흐름 기반 전용 병렬 처리** (Dataflow) |
| **클럭당 MAC 연산량** | 수십 회 (AVX 레지스터 수준) | 수천 회 | 수만 회 (10 ~ 100+ TOPS) |
| **메모리 병목 극복 방식** | 거대한 L2/L3 캐시로 지연 완화 | 고대역폭 메모리 (HBM, GDDR) 활용 | 레지스터 간 직접 데이터 전달로 메모리 접근 최소화 |
| **전력 대비 성능 (TOPS/W)** | 낮음 (범용 로직 오버헤드 큼) | 중간 (수백 W 전력 소모) | **매우 높음** (모바일·엣지 디바이스 필수) |
| **시뮬레이터와의 연계** | 본 과제의 2중 for문 순차 구현과 직접 대응 | 병렬 코어로 타일별 동시 MAC 수행 | 필터 가중치를 레지스터에 고정하고 패턴을 흘려보내며 즉시 합산 |

## 10. 보너스 과제 구현 (선택)

### 1) 1차원 배열 최적화 (`src/mac.py`, `src/matrix.py`)
2차원 리스트의 중첩 반복문(`for i in range(n): for j in range(n):`)은 매 반복마다 행 인덱싱 및 2차원 포인터 역참조 오버헤드를 발생시킵니다.
이를 길이 $N^2$인 1차원 리스트로 평탄화(Flatten)하여 단일 반복문(`for i in range(len):`)으로 연산하도록 최적화(`mac_1d`)를 구현하고 비교 측정한 결과입니다 (100회 반복 측정):

| 크기 ($N \times N$) | 2D 중첩 반복문 시간 (ms) | 1D 단일 반복문 시간 (ms) | 속도 향상 (Speedup) |
|:---:|:---:|:---:|:---:|
| 3×3 | 0.00090 ms | 0.00049 ms | **1.84배 향상** |
| 5×5 | 0.00162 ms | 0.00095 ms | **1.70배 향상** |
| 13×13 | 0.00802 ms | 0.00568 ms | **1.41배 향상** |
| 25×25 | 0.03364 ms | 0.02552 ms | **1.32배 향상** |

> **분석**: 단일 루프를 적용함으로써 2중 루프 분기 예측 비용 및 이중 인덱싱(`[i][j]`) 조회를 1차원 연속 메모리 접근(`[i]`)으로 줄여 평균 **1.3배 ~ 1.8배**의 뚜렷한 연산 속도 향상을 입증하였습니다.

### 2) N×N 패턴 자동 생성기 (`src/matrix.py`, `tools/make_data.py`)
- `make_cross(n, val, center_val, bg)`: $n \times n$ 크기의 중앙 십자가 패턴 자동 생성
- `make_x(n, val, center_val, bg)`: $n \times n$ 크기의 두 대각선 X 패턴 자동 생성
- 이 함수들을 통해 3×3부터 임의의 대형 크기까지 손쉽게 테스트 데이터를 프로그래밍 방식으로 생성하고 벤치마크에 재사용할 수 있도록 모듈화하였습니다.
